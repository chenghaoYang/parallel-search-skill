# api-protocol-v1：接着跑完并比较

读者用 Claude Code 把本 bench 收束、打分、写成 `bench/results.md`。命令都在仓库根目录 `仓库根目录` 执行。查询、针、原始答案都在现有文件里，下面不重贴。

## 1. 题

- `task_id`：`api-protocol-v1`。
- 人能看懂的问题（`golden.json` 的 `question`）：对比 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages、Google generateContent 的请求协议，并写明 DeepSeek 相对 OpenAI、智谱相对 Anthropic 的官方兼容入口。最终一份对比说明。
- 为什么选它：官方文档就是 golden。同一目标可以换方法。查询里不放标准答案，规模是唯一自变量。

## 2. golden 合同

12 条 claim，写在 `golden.json`。`scoring` 的意思：一条命中，当且仅当 `groups` 里每一组至少有一个针出现在全文，大小写不敏感，针不要求在同一句。`sourced` 还要 `hosts` 里任一主机名也出现。只计召回，不惩罚多写。更长的垃圾文本会占便宜，所以比较方法时必须同时看字数和检索次数。字数用 `score.py` 印出的 `chars`（全文 `len`），不要另算一套。

| id | claim |
|---|---|
| `openai-chat-path` | OpenAI Chat Completions 是 POST /v1/chat/completions。 |
| `openai-chat-messages` | Chat Completions 的对话放在 messages 数组里。 |
| `openai-responses-path` | OpenAI Responses 是 POST /v1/responses。 |
| `openai-responses-input` | Responses 的输入字段叫 input，官方示例里可以是字符串，也可以是内容数组。 |
| `anthropic-messages-path` | Anthropic 创建消息是 POST /v1/messages。 |
| `anthropic-system-toplevel` | Anthropic 正文写明：系统提示用顶层 system 参数，输入 messages 没有 system role。 |
| `google-generate-content` | Gemini 生成接口是 POST generativelanguage.googleapis.com 上的 models/*:generateContent。 |
| `google-contents-not-messages` | Gemini 对话在 contents 里，系统指令是单独的 systemInstruction，不是 OpenAI 那种 messages。 |
| `deepseek-openai-base` | DeepSeek 的 OpenAI 兼容 base URL 是 https://api.deepseek.com ，聊天路径是 /chat/completions。 |
| `deepseek-anthropic-base` | DeepSeek 另外给了一个 Anthropic 兼容 base URL：https://api.deepseek.com/anthropic 。 |
| `deepseek-reasoning-content` | DeepSeek 思考模式把思考过程放在 reasoning_content，和最终 content 分开。 |
| `zhipu-anthropic-base` | 智谱让 Claude Code 使用的 Anthropic 兼容地址是 https://open.bigmodel.cn/api/anthropic 。 |

针的全文在 `golden.json` 的 `groups`，不要抄进报告。

## 5. 完成定义

按顺序做。写报告时不要打开 `golden.json`。打分才用它。

1. 把 `runs/pplx-scale-1/01.json` 的 `answer` 原文，加上每条 citation 的 `title`、`url`、`snippet`，渲染成 `runs/pplx-scale-1/report.md`。不要改写，不要用 golden 补句。然后：

   ```bash
   python3 bench/score.py bench/runs/pplx-scale-1/report.md
   ```

2. 把 scale-4 的四份笔记（`01.json` 到 `04.json` 的 `answer` 和 `citations`）交给一次收束。收束者不得再联网，不得把 `golden.json` 的针抄进去当答案。只根据这四份笔记写成一份对比。产出 `runs/pplx-scale-4/report.md`。
3. 另把四份原始 `answer` 按 `01`→`04` 拼成 `runs/pplx-scale-4/expanded.md`，每段标明文件名。只拼 `answer`，不要拼 citations，不要拼 golden。对这个文件打分，记为扩展召回。再对 `runs/pplx-scale-4/report.md` 打分。用两次的命中差看收束丢了多少。扩展召回不是表里的方法行。

   ```bash
   python3 bench/score.py bench/runs/pplx-scale-4/expanded.md
   python3 bench/score.py bench/runs/pplx-scale-4/report.md
   ```

4. 写 `bench/results.md`。一张表，列：方法、fanout、命中/12、sourced/12、字数。两行只放两个方法的报告分（scale-1 用 `report.md`；scale-4 用收束后的 `report.md`，fanout 分别是 1 和 4）。表下写扩展召回的命中/12、sourced/12、字数，以及收束相对扩展少了几条命中。不要在本说明里预填分数。
5. 比较的是两份 `report.md` 的命中（hits），不是 expanded，也不是 sourced。若 4 路收束召回高于 1 路，下一档才是 8 路，方法 id 用 `pplx-scale-8`，仍然同一 golden。本轮只在 `results.md` 里写明可以进入下一档，不要先加查询、不要先跑。若没有更高，先写明原因，不要加路。
