## claims

### 坑与误解
- [C1] Temporal 官方口径：Workflow Execution 运行 "your application code, exactly once and to completion"，"in the presence of arbitrary load and arbitrary failures"；持久化靠 Event History 记录每步状态、崩溃后 "resume from the last recorded event" | src: https://docs.temporal.io/temporal | quote: "your application code, exactly once and to completion" | type: official
- [C2] 但 Temporal Activity 实际是 at-least-once：失败自动按 Retry Policy 重试，官方只「建议」幂等 | src: https://docs.temporal.io/activities | quote: "If an Activity attempt fails, it is automatically retried using its Retry Policy." / "We recommend that it be idempotent, so retries can be processed without duplicate side effects." | type: official
- [C3] 「durable execution = exactly-once」的最有力反驳来自官方文档的组合：Temporal 的 exactly-once 说的是 replay 出的代码路径/内部状态转移，外部副作用仍需幂等；社区实务博客讲得更直白 | src: https://www.ovasylenko.com/blog/at-most-once-side-effects-durable-workflow-engine | quote: "Every durable workflow engine has this window, and most of the marketing around 'exactly-once' is about how it is described rather than how it is closed." | type: secondary
- [C4] 确定性要求的形式各家不同：Temporal/Azure DF/DBOS 是命令序列 replay 确定性；Inngest 是「handler 每步重跑一遍、step 结果 memoize」，非确定性逻辑必须塞进 step.run()——约束仍在但性质不同 | src: https://www.inngest.com/docs/learn/how-functions-are-executed | quote: "Any non-deterministic logic (such as DB calls or API calls) must be placed within a step.run() call" | type: official
- [C5] Azure Durable Functions / Durable Task 确定性约束最重：禁 DateTime.Now、Guid.NewGuid、随机数、直接 I/O、env vars、static、threading；版本变更 "can break replay behavior" | src: https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-code-constraints | quote: "orchestrator functions must be deterministic: an orchestrator function replays multiple times, and it must produce the same result each time" | type: official
- [C6] DBOS 同样要求确定性：工作流 "should invoke the same steps with the same inputs in the same order"；担保分三层："Workflows always run to completion"、"Steps are tried at least once but are never re-executed after they complete"、"Transactions commit exactly once" | src: https://docs.dbos.dev/python/tutorials/workflow-tutorial | quote: "if called multiple times with the same inputs, it should invoke the same steps with the same inputs in the same order" | type: official
- [C7] Temporal 版本升级/non-determinism 是真实高频坑：community forum 反复出现 NonDeterministicException 案例（如 worker 跨时区导致 ZoneId.systemDefault 在 replay 时结果不同），官方建议用 sideEffect 固化 + WorkflowReplayer 测试 | src: https://community.temporal.io/t/non-determinism-after-versioning/7527 | quote: "This is not a problem that 'goes away' (non-determinism)... the worker that then picks up to continue the exec would do internal replay at which point you might see the non-deterministic error happen" | type: secondary
- [C8] 坑：Temporal 自托管运维重——Cassandra 扩展上限、sharding 反馈循环、需要专职团队 | src: https://news.ycombinator.com/item?id=40287341 | quote: "There are nasty feedback loops hidden in Temporal that turn small problems into very very large problems... You really need an entire team." | type: secondary
- [C9] 坑：容量规划——history service "ONE IO per shard"，且 "you can't change the shard count on existing clusters" | src: https://news.ycombinator.com/item?id=48314087 | quote: "you're limited to _ONE_ IO per shard in the history service... you can't change the shard count on existing clusters" | type: secondary
- [C10] 坑：可观测性/support——workflow 卡 In Progress、"errors aren't reported anywhere except buried in the event log"；自托管文档稀缺；计费单位 "actions" 让人困惑 | src: https://news.ycombinator.com/item?id=40309831 | quote: "the status reads in progress and errors aren't reported anywhere except buried in the event log" | type: secondary
- [C11] 坑：versioning 学习曲线，多年用户仍 "suck at" workflow versioning；Temporal 创始人在 HN 上承认 "The main problem is in forgetting to version code that changed" | src: https://news.ycombinator.com/item?id=24815640 | quote: "The main problem is in forgetting to version code that changed. But the system has protections against such cases." | type: secondary

### 同类引擎定位（新实体）
- [C14] AWS Step Functions：Standard = "exactly-once workflow execution"（内部状态转移持久化；除非配 Retry 否则任务不重跑），Express 异步 = at-least-once、同步 = at-most-once；Standard 最长跑一年；ASL 状态机非代码 replay，无确定性要求 | src: https://docs.aws.amazon.com/step-functions/latest/dg/concepts-standard-vs-express.html | quote: "Standard Workflows follow an exactly-once model, where your tasks and states are never run more than once, unless you have specified Retry behavior in ASL." | type: official
- [C15] AWS Durable Execution SDK（新！）：在 Lambda 内做 durable functions，TS/Py/Java/C#；"Automatic checkpointing"，步骤可选 "at-most-once or at-least-once semantics"，且官方明说 "Neither guarantees the step runs exactly once across the entire workflow" | src: https://docs.aws.amazon.com/durable-execution/ | quote: "The AWS Durable Execution SDK lets you build reliable, long-running workflows in AWS Lambda." | type: official

### 可能漏掉的维度
- [C25] 部署形态/爆炸半径四分法：library-in-app（DBOS 用你的 Postgres）vs service-you-call（Temporal/Restate）vs functions/queue 平台（Inngest/Hatchet）vs WASM runtime（Golem）；隔离性与运维面差异大于吞吐数字 | src: https://dreaming.press/posts/durable-execution-engines-for-ai-agents.html | quote: "The operational footprint and the failure blast radius differ more than the throughput numbers." | type: secondary
- [C26] 计费单位维度：Temporal Cloud 按 "actions"、Inngest 按 step、Trigger.dev 按 compute time、Step Functions 按 state transitions——单位口径完全不同，社区反映 "actions" 定义难懂 | src: https://news.ycombinator.com/item?id=40309831 | quote: "when they bill $N/million actions I have no idea what that means" | type: secondary
- [C27] 取舍维度：Inngest 用更简单运维换掉 Temporal 式 deterministic replay | src: https://markaicode.com/alternatives/temporal-alternatives/ | quote: "You trade Temporal's deterministic replay for a simpler ops model — Inngest doesn't reconstruct exact workflow state from a replayed event history the way Temporal does." | type: secondary
- [C28] signal 语义差异：LittleHorse CorrelatedEvents 可在不知 workflow ID 时扇出 signal；Temporal 系需知道 ID | src: https://littlehorse.io/compare/durable-execution | quote: "Signaling a running workflow requires knowing the workflow ID, increasing state management requirements." | type: official

## conflicts
- 「durable execution = exactly-once」各方口径打架：Temporal 官网 "exactly once and to completion"（C1）vs 自家 Activity at-least-once（C2）；AWS Step Functions Standard 自称 "exactly-once model"（C14）vs AWS Durable Execution SDK 明说 "Neither guarantees the step runs exactly once across the entire workflow"（C15）；Golem 营销 "every tool call exactly once"（C21）；Stonebraker VLDB 2026 论文称 durable execution "guarantees exactly-once execution of workflow steps"（https://www.vldb.org/cidrdb/papers/2026/p9-stonebraker.pdf）；实务派（ovasylenko, C3）认为只有引擎内部状态转移能做到 exactly-once，外部副作用最多 at-most-once。结论倾向：「工作流代码路径 exactly-once / 外部副作用需幂等」是所有引擎的真实语义，营销话术混淆了两者。
- Inngest 许可证描述：markaicode 表格写 "Closed (some OSS core)"，GitHub README 实为 SSPL+DOSP→Apache 2.0（C13 为准）。
- Temporal 自托管扩展性：HN 运维者称 "Temporal was a bad fit for us"（id=48314087）vs Temporal 员工同帖称 Temporal Cloud "currently handling 35 billion workflows per day"——自托管与托管云体验两极分化。
