## claims

### UCP
- [C1] UCP is transport-flexible: REST+JSON via OpenAPI 3.x; MCP and Embedded (EP) via OpenRPC; A2A via Agent Card. | src: https://ucp.dev/latest/specification/overview/ | quote: "supports multiple transports including A2A, MCP and APIs"; "the Checkout Capability can have a REST API binding or a MCP binding" | type: official
- [C2] Discovery: businesses publish a JSON profile manifest at /.well-known/ucp; platforms advertise their profile URI via the UCP-Agent header (sent on every request). | src: https://ucp.dev/latest/specification/overview/ | quote: "Businesses publish their profile at `/.well-known/ucp`; platforms publish their profile at the URI advertised in `UCP-Agent`" | type: official
- [C3] Checkout REST endpoints: POST /checkout-sessions, GET/PUT /checkout-sessions/{id}, POST /checkout-sessions/{id}/complete, POST /checkout-sessions/{id}/cancel; base URL from manifest "endpoint" field. | src: https://ucp.dev/latest/specification/shopping/checkout/rest/ | quote: "POST /checkout-sessions ... PUT /checkout-sessions/{id} ... POST /checkout-sessions/{id}/complete ... POST /checkout-sessions/{id}/cancel" | type: official
- [C4] Abstractions: services + capabilities named `{reverse-domain}.{service}.{capability}` (e.g. dev.ucp.shopping.checkout, .discount, .fulfillment); extensions via `extends` field; checkout session fields: id, line_items, buyer, status, currency, totals, links, payment, discounts; payment model separates instruments from handlers (shop_pay, google_pay, mock_payment_handler). | src: https://ucp.dev/latest/specification/overview/ | quote: "MUST use the format: `{reverse-domain}.{service}.{capability}`"; blog: "separating what consumers use to pay (instruments) from payment handlers (payment processors)" | type: official
- [C5] Versioning: date-based YYYY-MM-DD (manifest example "version": "2026-01-11"); per-capability negotiation picks highest common version; errors version_unsupported (HTTP 422), capabilities_incompatible. | src: https://ucp.dev/latest/specification/overview/ + https://developers.googleblog.com/under-the-hood-universal-commerce-protocol-ucp/ | quote: "separates protocol version selection from capability negotiation" ... "highest version (latest date)" | type: official
- [C6] Auth: businesses SHOULD authenticate platforms via API keys, OAuth 2.0, mTLS, or HTTP Message Signatures (RFC 9421); profile has top-level keys[] JWK Set (EC P-256/P-384, Ed25519); "Business-to-platform webhooks MUST be signed"; OAuth 2.0 authorization_code grant for identity linking; requests carry request-signature, idempotency-key, request-id headers; AP2 used for payments (ap2.merchant_authorization key). | src: https://ucp.dev/latest/specification/overview/ | quote: "Businesses SHOULD authenticate platforms to prevent impersonation and ensure message integrity" | type: official

### AP2
- [C7] AP2 spec v0.2 (repo tag v0.2.0, released 2026-04-28 per CHANGELOG) defines two mandate types — NOT IntentMandate/CartMandate. | src: https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md | quote: "AP2 defines two Mandate types: Checkout Mandate and Payment Mandate." | type: official
- [C8] v0.2 roles: Shopping Agent (SA), Credential Provider (CP), Merchant (M), Merchant Payment Processor (MPP), Trusted Surface (TS, non-agentic UI for user consent); Network verifies Payment Mandates; one entity may play multiple roles. | src: https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md | quote: "a UI surface that is trusted to get informed user consent"; "a single entity to play multiple (or even all) of the roles" | type: official
- [C9] Crypto: SD-JWTs secure both mandates; merchant issues "a merchant-signed JWT containing the Checkout"; closed Checkout Mandate bound via checkout_hash; open mandates "MUST include the agent's public key as a `cnf` claim"; checkout token "MUST be signed using a digital signature scheme (e.g., ECDSA) and not a deterministic signature"; vct strings version schemas (mandate.payment.1, mandate.checkout.open.1). Modes: Human Present (Direct) / Human Not Present (Autonomous). | src: https://github.com/google-agentic-commerce/AP2/blob/main/docs/ap2/specification.md | quote: "AP2 specifies the use of `SD-JWT`s for securing the Payment and Checkout Mandates." | type: official

### x402
- [C10] v2 (x402Version: 2): 402 response carries base64 `PaymentRequired` in PAYMENT-REQUIRED header; fields: x402Version, error, resource{url,description,mimeType,serviceName,tags,iconUrl}, accepts[]{scheme, network (CAIP-2 e.g. "eip155:84532"), amount, asset, payTo, maxTimeoutSeconds, extra}, extensions. | src: https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md | quote: "For HTTP, the canonical wire location is the base64-encoded `PAYMENT-REQUIRED` response header" | type: official
- [C11] Client sends `PaymentPayload` in PAYMENT-SIGNATURE header: {x402Version, resource, accepted (echoed PaymentRequirements), payload{signature, authorization{from,to,value,validAfter,validBefore,nonce}}, extensions}; server returns SettlementResponse in PAYMENT-RESPONSE header. | src: https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/http.md | quote: "Clients send payment data using the `PAYMENT-SIGNATURE` HTTP header." | type: official
- [C12] Facilitator: "an optional but recommended service", non-custodial ("does not hold funds or act as a custodian"); POST /verify checks payload vs requirements; POST /settle submits onchain and waits for confirmation, may return non-terminal settlement_pending with tx hash. Public x402.org facilitator is dev/testnet-only; production facilitators live on Base, Solana, Polygon, Avalanche; self-hosting possible. | src: https://docs.x402.org/core-concepts/facilitator.md | quote: "performs verification of the object based on the `scheme` and `networkId`"; "submits the payment to the blockchain" | type: official
- [C13] exact/EVM signature: EIP-3009 transferWithAuthorization (default for USDC, 65-byte signature; EIP-712 domain from extra.name/extra.version); Permit2 fallback via x402ExactPermit2Proxy.settleWithPermit for other ERC-20s; facilitator pays gas. Payment flows: `authorization` (verify→execute→settle) default, `upfront` (settle before handler). | src: https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_evm.md | quote: "Settlement is performed via the facilitator calling the `transferWithAuthorization` function on the `EIP-3009` compliant contract" | type: official
- [C14] v1→v2 changes: X-PAYMENT→PAYMENT-SIGNATURE, X-PAYMENT-RESPONSE→PAYMENT-RESPONSE; `maxAmountRequired`→`amount`; resource string→ResourceInfo object; networks→CAIP-2 ("base"→"eip155:8453"); schemes registered via .register() builder ("eip155:*" wildcards); "The facilitator supports both V1 and V2 protocols". | src: https://docs.x402.org/guides/migration-v1-to-v2.md + v1 spec | quote: v1 spec field "maxAmountRequired" Required "Required payment amount in atomic token units" | type: official

## conflicts
- AP2 mandate names changed between versions: v0.1 spec (tag v0.1.0, CHANGELOG 2025-09-16) uses VC-based IntentMandate/CartMandate/PaymentMandate — "The Intent Mandate is a separate verifiable credential", "verifiable credential “PaymentMandate” (bound to Cart/Intent mandate but containing separate..." (https://github.com/google-agentic-commerce/AP2/blob/v0.1.0/docs/specification.md). v0.2 spec (2026-04-28) replaces them with SD-JWT Checkout Mandate + Payment Mandate [C7]. Briefing's expected names IntentMandate/CartMandate are v0.1-era only.

## gaps
- UCP: exact format of `request-signature` header value (spec points to RFC 9421 HTTP Message Signatures but page excerpt didn't show header grammar).
- x402: facilitator fee model — facilitator.md does not specify pricing/commissions.
- AP2: whether IntentMandate semantics (autonomous "human not present" intent) survived v0.2 as fields inside Checkout Mandate — spec mention of open/closed mandate forms seen, but no explicit IntentMandate→Checkout mapping statement captured.
- UCP transport for EP (Embedded) OpenRPC details not opened.
