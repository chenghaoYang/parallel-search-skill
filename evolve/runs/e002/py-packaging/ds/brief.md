# Brief（R0）

## 任务
产出一份文档，帮用户理解当前 Python 包管理/项目管理工具的差异，并知道新项目该怎么选。

## 读者
会写 Python、但没跟紧 2024–2026 packaging 生态变化的人。可能还停留在 pip + requirements.txt 或 conda 的心智模型。要在 5 分钟内建立「现在有哪几类工具、差在哪、我该选哪个」的认知，再按需查细节。

## 范围内
- 5 个核心实体（种子词）：uv、pip（+ pip-tools）、Poetry（含 2.x）、PDM、conda / pixi（按行为差异拆成两行）。
- 4 个必答维度：锁文件（含 PEP 751 / pylock.toml）、workspace/monorepo、Python 版本管理、构建后端。
- 用户点名疑点（必须有明确结论）：
  1. PEP 751 / pylock.toml 是否已是「标准锁文件」？uv、pip 是否已支持？
  2. Poetry 2 是否已改用标准 `[project]` 表（PEP 621）？
- 其他用户需要知道的：从旧工具迁移路径（requirements.txt / Pipenv / setup.py / conda env）、CI 缓存要点、私有源/私有 index 配置。
- 依赖解析器/安装速度特征、全局工具运行（pipx 等价物）、生态定位（纯 PyPI vs conda-forge/科学计算栈）作为补充维度，视篇幅取舍。

## 范围外
- 不深入语言无关的 CI/CD 平台细节（只给 Python 生态相关的缓存建议）。
- 不覆盖 Python 语言本身特性、不覆盖 Rust/C 扩展编译细节（除非直接影响构建后端选择）。
- 不做性能基准测试（只引用官方/权威来源已发布的定性说法，不自己测速）。
- Hatch、setuptools、flit、maturin 等作为构建后端/次要实体，只在「构建后端」维度或「变体」一节里带过，不单独成行，除非调研中发现它是用户绕不开的选择（视 leads 决定）。

## 完成标准
- 文档在 9000 字符预算内（含来源节）。
- 5–8 条「一屏看懂」结论，两条用户点名疑点在其中有明确结论。
- 一张 taxonomy（分类轴 + 家族）+ 按维度的对照矩阵（原名字段，不意译）。
- 「用户须知的坑」覆盖迁移、CI 缓存、私有源。
- 「未决与置信度」列出仍空/冲突/二手来源的格子。
- 每个具体事实可追溯到 notes/ 里的一条 claim。
