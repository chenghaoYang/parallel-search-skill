# Taxonomy grid v0

状态：`✅` 一手来源 + 原句；`⚠` 只有二手；`⚔` 来源冲突；`❓` 缺口；`∅` 官方未写（已定向查过）；`—` 不适用。

## 分类轴（v0）

**接口平面：规范约束的是哪两端在说话。**

用这一轴回答「各自管什么」，并解释 ACP 缩写为什么会撞车：同名可以落在不同平面。R1 之后若这一轴解释不了矩阵里的主要差异，就换轴。

| 家族 | 平面 | 为什么暂归一类 | 实体 |
|---|---|---|---|
| 工具/上下文 | Agent ↔ 工具、资源、提示模板 | 把外部能力暴露给一个 agent 或宿主 | MCP |
| 对等委托 | Agent ↔ Agent | 把任务交给另一个 agent | A2A、ACP-IBM |
| 宿主客户端 | Agent ↔ IDE/应用宿主 | 编辑器或应用驱动一个编码 agent | ACP-Zed |
| 用户界面 | Agent ↔ 前端 UI | 把 agent 的过程渲染成界面事件 | AG-UI |

子区分（还不是第二根轴）：同在「对等委托」里，A2A 与 ACP-IBM 可能差在任务/工件模型 vs 消息模型，或其中一个已被并入另一个。用 D2、D8、D9 验证，不要提前合并实体。

## 维度

| ID | 维度 | 这一列回答什么问题 |
|---|---|---|
| D1 | peers | 两端角色的正式名称是什么？ |
| D2 | object | 规范里的核心消息或对象类型叫什么（原名）？ |
| D3 | transport | 规定了哪些传输；哪些被标记 deprecated 或 removed？ |
| D4 | discovery | 对端或能力如何被发现（机制原名）？ |
| D5 | lifecycle | 任务或会话状态由谁持有，状态机原名是什么？ |
| D6 | auth | 鉴权方案的原名（OAuth、header、API key、签名）？ |
| D7 | version | 当前规范版本号、日期、版本协商字段？ |
| D8 | governance | 谁治理（基金会、公司、仓库）？ |
| D9 | interop | 官方如何定位和另外几个协议的关系？ |

厂商支持不塞进协议行，单独一张表（下面）。自家变体只有在协议层或官方绑定层和参照协议不同时才另开实体行。

## 用户疑点

| 疑点 | 状态 | 负责 |
