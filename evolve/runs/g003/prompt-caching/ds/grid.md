# Taxonomy 网格 v0

分类轴：**缓存状态的形态**（谁创建边界、调用方是否必须改请求、状态是无名字的前缀还是可引用对象）。

这条轴要解释矩阵里的大部分差异：改不改代码（D1）、请求长什么样（D2）、有没有写入加价或存储费（D3）、谁控制 TTL（D4）、失效单位是前缀还是对象（D6）。若某家「不改代码」却按存储时长计费，或「必须打标」却没有断点字段，R1 后换轴。

## 家族（假设，R1 核实）

| 家族 | 一句为什么是一类 | 假设成员 |
|---|---|---|
| F1 自动前缀 | 服务端匹配稳定前缀；不改请求也可能命中 | OpenAI、DeepSeek；Gemini implicit、国内三家待核实 |
| F2 显式断点 | 不在内容块上打标就不缓存 | Anthropic |
| F3 命名上下文资源 | 先创建可引用的 cache 对象，再在后续请求里引用；常另计存储 | Gemini explicit |
| F4 网关适配 | 转发多家；缓存可能是透传、自建、或两者并存 | OpenRouter |

Gemini 预期跨 F1 与 F3，拆成两行，不要并成「Gemini 支持缓存」。

## 维度（后面所有表按此顺序）

| ID | 这一列回答什么问题 |
|---|---|
| D1 触发与边界 | 自动前缀、显式断点，还是先创建命名资源？不改代码会不会缓存？ |
| D2 请求形状 | 端点、字段、header、枚举的原名是什么？ |
| D3 命中计费 | 命中后输入怎么计价？写入是否加价？有没有存储费？ |
| D4 TTL | 默认活多久？能否自定？命中是否续期？ |
| D5 命中信号 | 响应里哪个字段表示命中、未命中或写入？ |
| D6 失效条件 | 哪些改动导致不再命中？ |
| D7 最小粒度 | 最少多少 token、块对齐、断点上限、哪些内容类型可缓存？ |
| D8 作用域 | 按组织/项目/key 隔离还是共享？精确匹配还是前缀？ |
| D9 覆盖面 | 哪些模型、哪些端点（chat / responses / batch / stream）？ |
