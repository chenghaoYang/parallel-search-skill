# 收束：成稿骨架、taxonomy、长度控制、审稿

收束只用 `notes/`，不搜索、不 spawn。每次收束都**从头重写** `report.md`，不是在上一版末尾追加。

## 成稿骨架

读者要在 5 分钟内建立认知，再按需往下查细节。层次固定，不要改顺序：

```
# <标题>
> 这份文档回答什么；截至日期；怎么读（2–3 行）

## 0. 一屏看懂
5–8 条结论。每条一句话，说出最重要的差异和它的后果。用户点名的疑点在这里先给结论。

## 1. Taxonomy
分类轴 + 家族划分（一张表或一棵树），每个家族一句「为什么它们是一类」。
再给维度清单：每个维度一句「这一列回答什么问题」。后面所有表都按这里的维度排。

## 2. 对照矩阵
每个维度（或几个相关维度）一张表：行 = 实体，列 = 该维度下的具体字段/取值。写原名（字段名、路径、枚举值），
不要意译。格子里放 [n] 引用。空格写 ❓，官方未写写 ∅。

## 3. 变体与适配层
「兼容 X」的实体相对参照协议差在哪：一张差异表（实体 × 差异点），再加少量必须解释的散文。

## 4. 用户需要知道的坑
每条：现象 → 原因 → 怎么处理 [n]。按踩中的概率排序。

## 5. 未决与置信度
还空着/冲突/只有二手来源的格子；官方文档之间的矛盾；时效风险（页面日期、预览功能）。

## 来源
[n] 标题 — URL（官方在前；去重；只列正文实际引用过的）
```

## Taxonomy 写法

- 先分家族，再比细节。家族按「分类轴」划（例如：请求形状继承自谁、状态放在哪一端）。分类轴要能解释矩阵里大部分差异；解释不了就换轴，并在 `log.md` 记下换轴理由。
- 维度彼此正交，名字是问题而不是名词堆（「对话历史谁来保存？」好过「状态」）。
- 同一事实只在一个地方写全。别处可以标「见 §k」，但句中的具体事实仍带原处的 `[n]`；`[§k]` 不是来源。

## 长度控制（不许越改越长）

- 任何快照 `len(report.md) ≤ budget`（含来源节）。超了就压缩，不能交。
- 第 2 轮起，每次重写要在 `log.md` 写：新增了什么、为了它删了/压了什么、字数前后变化。
- 分级：P0 = 用户点名的疑点、taxonomy、核心矩阵，不删；P1 = 坑、适配差异，压成表；P2 = 背景、历史、次要实体，先删。
- 压缩手段按顺序：删重复 → 散文改表格 → 合并相邻行 → 次要实体并成「其他」一行 → 删 P2。
- 不要用「详见来源」糊弄正文；矩阵里该有的字段名必须在。

## 引用

- 正文每个具体事实后面带 `[n]`，`[n]` 指向来源节。来源节里的 URL 必须来自笔记的 `src`。「一屏看懂」同样如此，不能只标 `[§k]`。
- 来源节里的地址照抄笔记 `src` 的完整 `https://` URL。不要去掉协议，不要用花括号或省略号把几条合成一条。重写时可以删掉正文已不再引用的条目，不能把还在引用的 URL 写成缩写。
- 只有二手来源支撑的事实加「（二手）」，或放进第 5 节。
- 笔记里互相冲突的，正文写能确认的那一边，另一边和原因写进第 5 节。

## 核验（终审工人用）

核验清单怎么挑、核验简报怎么写，见 SKILL.md「终审与停止」和 `references/worker.md`。
核心差别：核验工人**回原页**核对，不是拿成稿对笔记——笔记本身可能就是错的源头。

主 agent 收到判定表后：

- `wrong` 且附了页面原句 → 按原句改正，`[n]` 保留。
- `wrong` 没附原句、`not-on-page`（页面打开了但没写）→ 删除或移到第 5 节标「未核实」。
- `not-on-page`（页面打不开）→ 不删，标「未核实」；可能是网络或站点问题，不等于主张错。
- `走样`（成稿≠摘录）→ 改回摘录的说法。
- `confirmed` → 不动。
- 一屏/坑与矩阵对不上的概括句 → 改成与矩阵和笔记原句一致，并带上该格的 `[n]`。

没进核验清单的主张不另派工人，靠「每条具体事实追到笔记 `[C#]`」自查；被截断没核上的在 §5 写明。
把判定汇总写进 `<dir>/audit.md`，改完再跑一次 `roundstat.py`；若有 `cite:`，按笔记 `src` 补回完整 `https://` 和缺的 `[n]`。终稿同样受 `budget` 约束。
