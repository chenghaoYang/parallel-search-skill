# 把查到的东西讲清楚

整合不是把研究者的笔记拼起来。先找出哪些结论真正回答了用户的问题，再挑支撑它们的证据，解释差异为什么重要。资料不足以支持明确结论时，给出范围有限的回答和还缺的证据。

## 选适合问题的表达

开头直接回答最重要的问题，让读者知道该如何理解或选择。后文可以解释机制、比较取舍、展示案例或说明限制，顺序取决于任务，不需要固定的七节结构。

- 比较可对齐的选项时，表格能让差异更清楚；列只放会改变判断的维度。
- 解释一个机制或论证因果时，用连贯段落，别把每句话都拆成小标题和项目符号。
- 读者要采取行动时，说清适用前提、第一步和如何判断结果，不要求每份研究都有检查清单。
- 不确定性放在相关结论附近。如果问题仍有重要争议，再集中解释，不为形式单列空洞的“置信度”章节。

标题用内容本身命名。自然地解释术语、举必要的例子，不以“建立认知框架”“赋能决策”之类空话代替解释。也不要强行把不同选项分成对称的几派；分类有助于理解才使用。

## 来源随结论走

关键事实的链接放在它支撑的句子或段落附近，直接链接和编号引用都可以。编号引用要能在同一文件找到完整来源；不要把“见上一节”当成证据。重写后检查链接还在、引用仍支持现在的表述。

区分原始材料报告的结果与自己的解释。论文结果保留数据集、任务、比较基线、硬件或其他会改变结论的设置；不要把选择器开销忽略后称为端到端省算力。对论文的复述、你的推算和建议不应共用一种确定口气。

交付前检查最可能误导读者的地方：结论是否超过证据范围，数字是否抄对，否定或排他说法是否漏掉例外，冲突是否解释清楚。可以自己回原页，也可以请独立研究者核验。只对照二次笔记不能排除原始摘录错误。

打不开来源就标出这一限制，寻找其他允许访问的一手入口；不能把无法访问当作反证。没有证据的事实缩小、降级或删去，不要靠增加引用数量掩盖薄弱支持。

## 篇幅和文件按需要来

先删重复、无关背景和不影响判断的细枝末节，再调整结构。不要为了缩短而把解释压成读不懂的缩写表。补充重要证据可以让稿子合理变长，但要遵守用户给定的长度限制。

单篇回答或 `report.md` 通常足够。确实需要反复查询大量细节时，可另建 `atlas.md`、附录或 `details/`；文件名和形式都可以随任务调整。主回答仍要独立回答问题，不让读者为一个简单结论跳几次文件。用户指定的输出路径、格式或总篇幅优先，不用附录绕过限制。

有了好稿就局部修订，不必每收到一份笔记都全文重写。长任务或明确要求过程记录时再保留快照和简短日志，记真正改变方向或结论的证据即可。

## 旧版检查工具

`notes_lint.py` 能检查旧 C# 笔记格式中的字段遗漏；自由格式笔记会标为“未评估”，不是通过或失败。`roundstat.py` 可显示已有报告、快照、网格的统计，显式传入 `--budget` 才检查字符上限。可选的 `--legacy-layout` 仅用于排查旧版编号引用和分层稿件约定。

这些工具只查形式，不会核验来源真假、结论是否正确或文字是否好读。仓库历史 `bench/` 与 `evolve/` 的部分指标仍依赖旧版章节和 C# 格式；新写法缺少这些标记时不能直接解释为研究质量下降。修改评测应另行设计并保留历史结果，不为旧指标恢复僵硬输出。
