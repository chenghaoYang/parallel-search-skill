# 工人：简报模板、笔记格式、规则

## 简报模板（主 agent 填好后原样发给工人）

```
轮次/编号：r<轮>-<slug>
窄问题：<一句话。只问一个实体、一个文档站，或一簇指定格子>
要填的格子：<grid.md 里的坐标，或维度列表>
上下文：<为什么问这个；R2 起写明上一轮查过哪些页、哪里冲突、原句是什么>
不做什么：<不写综述；不查别的实体；不回答整道大题>
来源政策：一手来源优先（域名：…）；二手来源可以记，但标 secondary；搜索引擎的综合答案只当线索
笔记路径：<dir>/notes/r<轮>-<slug>.md
返回：≤ 10 行（见下文「返回消息」）
```

## 笔记格式（写进笔记文件，不要贴回主上下文）

```
# r<轮>-<slug>
question: <窄问题原文>
checked: <实际打开过的页面 URL，逗号分隔>

## claims
- [C1] <一条原子主张，含具体字段名/路径/数值> | src: <URL> | quote: "<页面原句，≤ 40 词>" | type: official
- [C2] … | type: secondary

## conflicts
- <主张 A 与主张 B 冲突：各自 URL 与原句；可能原因（版本/地区/模型差异）>

## gaps
- <被问到但没查到的格子；查过哪些页；为何没有>

## leads
- <范围内但不属于本简报的新实体、新维度、新疑点，一行一个>
```

约束：

- 每条主张原子化：一个事实一条，带具体名字（端点、字段、header、枚举值、base URL）。
- `src` 必须是完整 URL（`https://…`），不许写相对路径、站内简称或脚注编号；否则收束时追不回来源。
- `quote` 必须是页面原文（中文页面就摘中文），不改写。拿不到原文的主张不要写进 claims，写进 gaps。
- `type`：`official` = 厂商官方文档/参考/changelog/官方仓库；`secondary` = 其他一切。
- 看到页面上的更新日期或版本号，就写进主张（时效性）。
- 上限：≤ 40 条主张，≤ 8000 字符（硬上限，`notes_lint.py` 会标出超长笔记）。宁可少而准。
- 预算：一个工人大约 20–25 次工具调用。整份规范（OpenAPI、几万行的文档）下载下来只 grep 需要的段落，不要逐段通读。

## 工人规则

1. 只回答自己的窄问题。不读别的工人的笔记，不写最终文档。
2. 先找一手来源页面并打开它（WebFetch）；搜索（WebSearch、`pplx-safe search`）只用来找页面。
3. 同一事实官方文档之间打架，或文档与实际行为描述不一致，记进 conflicts，不要自己裁决成一句。
4. 否定、排他、起始版本类主张（「不支持」「只有」「自 vX 起」「未提及」）最容易错：WebFetch 返回的是按你的提问做的摘要，
   摘要里没有不等于页面上没有。写这类主张前，用直接的提问再取一次（「这一页是否提到 X？给原句」）；版本起点要找
   changelog / release notes 里最早的相关条目，不能只看最新几条。仍拿不准就写进 gaps，列出查过的页。
   简报要你反证一条主张时，只找反例：找到一手反例就写成 claim，并在 conflicts 里写明它推翻了哪条；找不到就写明查过哪些页。
5. 超出简报范围但重要的东西只记进 leads，一行一个，不展开调研。
6. 返回消息（≤ 10 行）：
   ```
   notes: <笔记路径>
   claims: <n>（official <a> / secondary <b>）
   filled: <填上的格子>
   gaps: <没填上的格子，一行>
   conflicts: <n>，最重要的一条：<一句话>
   leads: <最重要的 1–3 条>
   ```
