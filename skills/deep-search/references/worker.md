# 把独立的问题交给研究者

当拆题能减少等待或让不同证据得到充分检查时再并行。按来源站点拆分适合文档比较，按方法或争议拆分适合研究综述；不要强求每个主题都能装进实体 × 维度的表格。

给研究者足够的上下文，但不用复制完整会话。一次简报说明：

- 要回答的问题，以及它对用户为什么重要
- 已知信息、已读来源或已有结论；哪些地方仍不确定
- 范围和边界，尤其是相邻任务正在查什么
- 需要交回的结果、来源和限制；有文件要求时给明确路径
- 真正存在的时间、工具或模型限制

例如：“比较这些方法如何选择视频帧，重点是问题是否已知、选择器额外开销和漏掉短事件的风险。先读原论文的实验设置和消融，不要把不同数据集的分数直接排序。交回最有用的判断、支撑链接及仍需核对的问题。”这是简报的粒度示例，不是固定字段表。

## 研究者怎么做

围绕自己的问题读最相关的原始资料。标准术语、别名、用户的表达都可以作为搜索入口；结果不对时调整查询，不要被简报里的词表锁住。

区分原文事实、你的推断和建议。关键事实保留完整 URL 及能定位的章节、页码、表格或必要的短摘录。版本、测试条件和访问日期有影响时一并记下。引用来源自身的限制，不把一篇论文的实验结果说成普遍规律。

遇到矛盾，解释它是否来自版本、对象或测量条件差异；无法判断就保留双方证据。重要的否定或排他结论应主动找反例；打不开页面或找不到一句话时，说明实际查过什么，不凭记忆补全。

先把有用结论交回来，再附证据或笔记路径。新发现会改变主任务方向时及时报告，不必等所有次要问题查完。范围外但很有价值的发现简短提醒，避免自行扩成另一项研究。读不到来源、不能写文件或工具失败时明确说出来；可以把必要内容直接交回，让主 agent 保存。

## 笔记的重点是能追溯

笔记可以是简短段落、列表或表格。让接手的人分得清哪条结论由哪个来源支撑，以及哪些地方还没解决即可。若需要反复汇总大量原子事实或使用旧评测，可选用兼容格式：

```markdown
# <问题>
checked: <实际读过的 URL>

## claims
- [C1] <原子事实及适用范围> | src: https://example.org/source | quote: "<必要的短摘录>" | type: official

## conflicts
- <相互矛盾的说法、各自来源和可能原因>

## gaps
- <未解决的问题，以及查过哪些资料>

## leads
- <值得主 agent 注意的新线索>
```

这里的 `official` 是旧脚本的“官方来源”标签，不是质量保证；原论文、数据集和二手分析仍应说明真实来源类型。短摘录不是每个事实的必填项，页码或章节也可以定位；但旧 `notes_lint.py` 只识别这个格式中的 `src`、`quote` 等字段，会对其他写法提示“未评估”。不要为了满足脚本伪造摘录或来源类型。笔记长短取决于问题，不设统一的主张数和工具调用次数。

## 独立核验

适合把可能改变结论的主张交给另一位研究者回原始材料核对。给出要核的原句、引用来源、适用条件和具体疑点；请其说明“支持”“需缩小范围”“与来源冲突”或“无法核实”，并附依据。不要把来源不可访问与来源明确否定混在一起。

核验结果能改变稿件就修改；缺少证据的地方保留限制。核验者不必重做整项调研，也不必使用固定判定码。
